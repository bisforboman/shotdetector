# FastYuv for 10-bit on x64: merge now, faster later (2026-10-18)

### Question

FastYuv's 10-bit 4:2:0 converter (#412) reproduces x86's bytes exactly, and ARM's CI matches x64 on both 10-bit
samples. But on x64 it is slower than the default path for small 10-bit video (854x480: 3.1 s to 7.5 s through the
ffmpeg executable, 2.6 s to 9.3 s in-process; 1080p about even), because each chroma row is filtered again for every
output row that reads it. Today a FastYuv user with 10-bit video silently gets the default path. What should ship?

### Choices

1. Merge, speed-up later (recommended): the same results everywhere, slower only on x64 for small 10-bit video with
   FastYuv opted in; a "filter each chroma row once per frame" follow-up goes to the backlog's Next; consistent with
   the decision that a set converter is used as set (2026-10-18-fastyuv-x64-in-process.md). 2. Make it faster first.
   3. 10-bit FastYuv off x86 only (reverses that decision for 10-bit).

### Answer

**1, merge, speed-up later.** The follow-up is in docs/backlog.md's Next. It can be additive: a batch interface
beside `IYuv420P10Converter` (as `IYuv422Converter` sits beside `IYuv420Converter`), which the pipeline type-tests for,
so the interface shipping in #412 needn't change.

Landed the same day (`IYuv420P10FrameConverter`, docs/fastyuv-10bit-422.md "As built (10-bit 4:2:0)"): on 4 shared
x64 vCPUs, 854x480 10-bit with FastYuv took 3.9 s instead of 5.8 s through the executable and 3.8 s instead of 5.1 s
in-process (default path 3.5 s), 1080p 10.3 s instead of 12.3 s in-process (default 12.1 s); the same bytes.
