# FastYuv for 4:2:2 and 10-bit: scope, API, rotation, samples (2026-10-18)

### Question

docs/fastyuv-10bit-422.md scoped what it takes for ShotDetector.FastYuv to give x86's results on ARM for 8-bit 4:2:2
and 10-bit 4:2:0 too, as it does for 8-bit 4:2:0 (docs/decisions/2026-10-17-arm-results.md). 4:2:2 (even height) runs
the same x86 converter FastYuv already ports with the chroma row `y` instead of `y >> 1`, reproduced exactly by a
prototype; 10-bit runs swscale's MMXEXT vertical scaler and output, 3-4 times FastYuv's converter, and its large
differences aren't explained yet. Four questions: how far to go, the public API, rotated frames, and samples.

### Choices

1. Scope: (a) 4:2:2 now, 10-bit later, once a prototype reproduces x86's bytes; (b) 4:2:2 now plus a 10-bit prototype;
   (c) both fully; (d) hold.
2. API (`IYuv420Converter` is public and 4:2:0 only; package validation against `ApiBaselineVersion` refuses a new
   member): (a) a new public interface beside it, which FastYuv's `SwscaleYuv420` also implements, the pipeline
   type-testing the object given as `DetectionOptions.Yuv420Converter`; (b) a default interface member on
   `IYuv420Converter`; (c) a breaking change in 4.0.
3. Rotation: the yuv420p pipeline turned the planes before converting (ffmpeg's transpose; in-process FrameWriter),
   which for 4:2:2 at 90 and 270 changes the subsampling: (a) keep skipping FastYuv for turned 4:2:2; (b) a
   source-coordinate converter: convert the planes as decoded and turn the converted BGR afterwards, as OpenCV's
   cv::rotate does after converting.
4. Samples for ci.yml's arch comparison: an unrotated 4:2:2 sample, required on ARM with FastYuv; and an odd-width
   sample, reported, not required, until its first ARM table is read.

### Answer

1. **(a)**: 4:2:2 now; 10-bit stays Maybe in docs/backlog.md until a prototype reproduces x86's bytes.
2. **(a)**: `IYuv422Converter` (src/ShotDetector), with `ForColor` and `RowToBgr` like `IYuv420Converter`'s;
   `SwscaleYuv420` implements both; no new `DetectionOptions` property.
3. **(b)**: the YUV pipelines (4:2:0 too) send the planes as decoded and turn after converting (`CvResize.ResizeYuv`),
   so rotated 4:2:2 uses FastYuv and `sintel_rotated_422.mp4` is required. For 4:2:0 this also fixes turned video with
   an odd decoded size, which turning the planes got wrong (FastYuv's stats differed from the default path's on a
   320x237 4:2:0 clip turned 90 degrees).
4. **Both**: `samples/sintel_422.mp4` (h264 yuv422p, required) and `samples/informational/sintel_oddwidth.mkv` (VP9
   at 853x480: libx264 refuses odd widths for subsampled formats; reported). The premise that odd widths take swscale's
   C path on x86 turned out wrong for 8-bit: at the same size, odd-width yuv420p and yuv422p take the unscaled SSSE3
   converter too, and FastYuv reproduces it (checked with FFmpeg 8.1.3 against `-cpuflags -ssse3`, 0 pixels off), so
   FastYuv takes odd widths as it always did for 4:2:0; the sample stays reported, as chosen, until its ARM table is read.
