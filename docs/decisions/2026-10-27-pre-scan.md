# The packet pre-scan (2026-10-27)

### Question

The pre-scan is only 1-4% of a run on local disks. Which pieces should be built?

Detection on a file reads it twice: the probe goes over every packet for its pts (`MediaProbe.Packets`, or ffprobe's
`packet=pts`), then the decoding pass. The packet list gives every frame's timecode (`Position(frame)` is
`_pts[PacketOf(decoded time)]`, so frame numbers skip where the decoder drops a frame, as OpenCV's do), the frame count
(progress, chunk boundaries) and the seeks (`-s`, each chunk's start). MPEG-PS, whose packets don't all carry a pts,
pays more: a whole decoding pass for the frames' timestamps (`FrameTimestamps`, as OpenCV labels its frames there) before
detection decodes the file again.

Measured on 4 CPUs: the packet scan is 1-5% of a run on a local disk (h264 mp4, MPEG-2 TS); MPEG-PS's decoding pass is
25-35% of its run (5.1-5.4 s of 14.8-23.6 s in-process). On a slow share the scan costs size / throughput up front
(+19% on a 4-minute 1080p file at 100 MB/s).

### Choices (any of them)

1. **MPEG-PS: no extra pass.** In-process, take each frame's timestamp from the frame as detection decodes it (its pts
   when set and non-zero, else its packet's dts: the pass's own rule), and take the pass only when something needs them
   all first (a start time, the executable, a read of a later frame). Progress counts against the stream's frame count
   or duration × rate meanwhile.
2. **mp4/mov timing-only scan.** FrameReader's probe reads the sample tables and skips `mdat`'s payload (libavformat
   computes the pts from the tables): the scan reads kilobytes instead of the file.
3. **Concurrent scan for mkv/ts, sequential path.** The packet scan runs alongside decoding instead of before it; a
   frame's label is final once the scan is past its time (the whole scan where timestamps go back). Gains where reading
   is slow and the file fits the page cache; chunked runs keep the scan first.

### Answer

**All three** (the owner, 2026-10-27), as three pull requests in that order, each with results identical everywhere
(scene and stats CSVs, every detector, 0.7.2 and 0.7.1, in-process and executable, chunked and sequential).

### How MPEG-PS's timestamps arrive (choice 1)

The design memo assumed the frame labels would then be the identity (frame k is packet k). They aren't, not even on a
clean file: the last frame of every sample PS (flushed out of the decoder without a pts or dts) is looked up as packet 0,
and in a PS joined to itself (timestamps that start over, as in VOB sets) about 600 frames are labelled by earlier
packets' times. So `PacketOf` keeps its rule, over the timestamps that have arrived so far (this frame's included): it
decides where its search stops inside them (a match, or a timestamp past the frame's time), and where it would run past
the last one, the answer depends on frames still to come and the decoding pass runs there and then (none of the sample,
cut, holed or joined PS files needed it). The first shot's start, asked for before any frame, is taken with the first
frame. Deinterlaced reads keep the pass (yadif's frames carry other times), as do the executable and anything that seeks
by the timestamps; a read that stops early leaves the rest to the pass.

Measured (this container, 4 CPUs, in-process, one run each, every detector at once): the sample PS files and cut, holed
and joined copies took 2.2-4.7 s instead of 2.7-5.5 s, results byte-identical in both modes. sintel_mpeg2.mpg alone
(default detector, four interleaved runs each): 1.81-1.98 s instead of 2.17-2.62 s wall, 3.3-3.5 s of CPU instead of
4.1-5.1 s.
